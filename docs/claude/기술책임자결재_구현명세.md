## 1. 선행 UI 작업 (기술책임자 결재 페이지 작업 전 완료 필요)

### 1-1. reportModify 모달 — 수리/불가/초기화 버튼 추가

**위치:** 성적서 수정 모달 좌측 하단 '성적서작성' 버튼 우측

| 버튼 | 동작 | 활성색상 | 비활성(NORMAL) 색상 |
|---|---|---|---|
| 수리 | report_status = REPAIR | 하늘색 | 연한 회색(기본) |
| 불가 | report_status = IMPOSSIBLE | 빨간색 | 연한 회색(기본) |
| 초기화 | report_status = NORMAL | 노란색(항상) | — |

- 3개 버튼은 여백 없이 붙여서 표시
- 수리/불가 처리 전 `gMessage()` confirm 필수
- 초기화 클릭 시 수리·불가 버튼 색상 → 기본 회색으로 변경

**수리/불가 처리 시 초기화 대상 (member_id 제외)**

| 컬럼 | 초기화 값 |
|---|---|
| write_status | IDLE |
| write_datetime | NULL |
| work_status | IDLE |
| work_datetime | NULL |
| approval_status | IDLE |
| approval_datetime | NULL |
| file_info (type = origin, signed) | is_visible = 'n' |

- 실무자 결재 완료(`work_status = SUCCESS`) 상태이면 수리/불가 처리 불가

---

### 1-2. workApproval 페이지 — 상태변경 열 추가 + 행 색상

**열 추가:** 리스트 마지막 열 'PDF' 우측에 '상태변경' 열 추가

- 셀 구성: '수리' 버튼(세로), '불가' 버튼(세로), '초기화' 버튼(가로 — 개행 없음)
- 동작은 1-1과 동일 (실무자 결재 완료 시 수리/불가 불가)

**행 전체 배경색 (체크박스 제외)**

| 상태 | 배경색 |
|---|---|
| REPAIR | 연한 하늘색 |
| IMPOSSIBLE | 연한 빨간색 |
| REJECTED | 연한 노란색 |
| RESUBMITTED | 연한 파란색 |
| work_status = SUCCESS (실무자결재 완료) | 연한 초록색 |

> 기술책임자 결재까지 완료된 성적서는 workApproval 리스트에 표시되지 않음

---

### 1-3. reportUpload 모달 — type 파라미터 분기 처리

호출 시 `type` 파라미터 추가: `work`(실무자) / `manager`(기술책임자)

| 구분 | type=work | type=manager |
|---|---|---|
| 모달 타이틀 | 기존 타이틀 유지 | 기술책임자용 타이틀 |
| 업로드 가능 형식 | xlsx (기존) | xlsx, pdf |
| 업로드 가능 조건 | 기존 조건 유지 | approval_status = SUCCESS 인 성적서만 |
| 업로드 후 동작 | 기존 유지 | 파일 교체만 (결재 정보 변경 없음) |

## 3. 주요 기능 상세

### 3-1. 성적서 반려처리

**진입 경로:** 좌측 상단 '반려' 버튼(체크 기준) 또는 '결재자' 열의 '반려' 버튼(단건)

**검증 조건 (반려 불가 케이스)**
- approval_status IN ('READY', 'PROGRESS', 'SUCCESS') → 반려 불가

**처리 흐름**
1. 검증 통과 → `reportReject` 모달 호출 (`gModal`, sm 사이즈)
   - 모달 타이틀: 단건 → `성적서번호`, N건 → `성적서 번호 [XXX] 외 N건 반려`
   - 내용: 반려사유 textarea (resize 불가, 기본 6줄)
   - 버튼: '반려'(isConfirmed), '닫기'
   - 반려사유 미입력 시 프론트 검증으로 차단
2. 반려 클릭 → `gLoadingMessage('반려처리중입니다...')` 표시
3. 백엔드 처리:
   - report_status = 'REJECTED'
   - status_remark = 반려사유
   - work_datetime, work_status, approval_datetime, approval_status 초기화
   - file_info (ref_table_name='report', type='signed') → is_visible = 'n'
   - report_job_batch 중 해당 성적서 PROGRESS 상태인 배치 → CANCELED 처리
   - report_job_item 데이터는 이력 보존 (삭제/초기화 안 함)
4. 완료 → 모달 닫힘 + 그리드 재조회 (반려된 성적서는 리스트에서 사라짐)

---

### 3-2. 성적서 결재 (다중결재)

> **UI 골격만 구현. 클릭 핸들러는 추후 별도 지시.**

- 좌측 상단 '다중결재' 버튼
- '결재자' 열의 '확인' 버튼 (단건)

---

### 3-3. 일괄다운로드 (EXCEL / PDF)

**방식:** 서버사이드 ZIP 스트리밍 (`StreamingResponseBody` + `ZipOutputStream`)

- 1건: 단순 파일 다운로드
- N건: 단일 ZIP으로 묶어서 반환 (임시 디스크 파일 미생성 — 스트리밍)
- 진행 표시: 파일 수를 포함한 로딩 스피너 (`N개 파일 ZIP 준비 중...`)
- 비정상 종료 시 응답 스트림 닫힘, 쓰레기 파일 없음

---

### 3-4. 성적서 취소

**진입 경로:** 좌측 상단 '일괄취소' 버튼 또는 '취소' 열의 '취소' 버튼(단건)

- 대상: approval_status = SUCCESS인 성적서만
- confirm 후 진행
- 초기화 대상: approval_status → IDLE, approval_datetime → NULL
- 유지 대상: approval_member_id (초기화 안 함)
- 완료 후 그리드 갱신 → '결재자' 열에 '반려'/'확인' 버튼 재표시

---

### 3-5. 다중업로드 (EXCEL / PDF)

- reportUpload 모달 재사용 (`type = 'manager'` 파라미터 전달)
- 대상: approval_status = SUCCESS인 성적서만
- 파일 교체만 수행 (결재 정보 변경 없음)
- 업로드 전 "파일이 교체됩니다" confirm 필수

## 4. 백엔드 구현 항목

| 항목 | 내용 |
|---|---|
| ReportStatus enum | NORMAL / REPAIR / IMPOSSIBLE / REJECTED / RESUBMITTED |
| 수리/불가/초기화 API | PATCH — 상태 변경 + 데이터 초기화 |
| managerApproval 조회 API | GET — work_status=SUCCESS 기준 페이징 조회 |
| 반려 API | PATCH — 다건 처리, 배치 CANCELED 포함 |
| 취소 API | PATCH — approval 정보 초기화 |
| 일괄다운로드 API | GET — StreamingResponseBody ZIP 스트리밍 |
| reportUpload 수정 | type=manager 분기 처리 (파일 교체 전용) |
